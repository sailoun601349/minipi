## 1. 先看清 pi-web 到底是什么

我把 `E:\pi-web` 摸了一遍。它不是「pi 的网页版聊天」，是**一套完整的代码工作台**：

| 维度 | pi-web 的实际能力 | 组件/模块证据 |
|---|---|---|
| **会话管理** | 按项目查找/继续/重命名/导出/删除，上下文占用、花费、压缩信息 | `SessionSidebar.tsx`、`session-reader.ts`、`session-stats.ts` |
| **分支能力** | 两种分支：新会话 / 从此处编辑；树状导航 | `BranchNavigator.tsx`、`session-tree.ts`、`session-family.ts` |
| **文件工具** | 浏览/上传、Git Diff、预览源码/Markdown/图片/音频/PDF/DOCX、变更自动刷新 | `FileExplorer.tsx`、`FileViewer.tsx`、`file-types.ts` |
| **Git 集成** | worktree 切换、多 worktree 会话归组、diff/status | `worktree.ts`、`git-changes.ts`、`git-status.ts` |
| **模型配置** | Provider 登录、API Key、模型测试、插件包、技能管理 | `ModelsConfig.tsx`、`PluginsConfig.tsx`、`SkillsConfig.tsx` |
| **高级工具** | 子代理、扩展状态栏、扩展 widget、终端、项目信任 | `subagent-*.ts`(8 个)、`ExtensionStatusBar.tsx`、`ProjectTrustDialog.tsx` |
| **代码视图** | 代码高亮、ANSI 渲染、Mermaid、Frontmatter 卡片 | `AnsiText.tsx`、`MermaidBlock.tsx`、`FrontmatterCard.tsx` |
| **部署形态** | 本地 Web 服务（127.0.0.1:30141），有 HTTP Basic Auth 与远程访问说明 | `bin/pi-web.js`、`web-auth.ts`、`README.zh-CN.md` |

**规模感**：`lib/` 下 **150+ 个模块**，`components/` 33 个组件，几乎每个 `.ts` 都配 `.test.mjs`。

### 关键洞察

pi-web 有一个**极重要的先例**值得抄：`lib/chat-only.ts`

```ts
export const CHAT_ONLY_RESOURCE_LOADER_OPTIONS = {
  noExtensions: true,
  noSkills: true,
  noPromptTemplates: true,
  noThemes: true,
  noContextFiles: false,
  systemPrompt: " ",
  appendSystemPrompt: [" "],
  ...
};
```

**pi-web 官方自己就提供了「chat-only」模式**——把扩展、技能、提示模板、主题全关掉，只留对话。
这说明「退化到纯 chat」是 Pi 生态里**被官方认可的用法**，不是你们在逆着架构走。这是个好消息。

## 2. 真正的差异不是「迷你」，是「角色」

用一句话把两者分开：

> **pi-web 是「我坐下来用它干活」的工作台；minipi 是「我在干别的时它随时能帮我」的影子。**

这个区别带来一组硬约束，比"窗口小"深刻得多：

| 约束 | pi-web（工作台） | minipi（影子） | 设计后果 |
|---|---|---|---|
| **注意力** | 打开它 = 专注工作 | 它在**别的 App 上面**，用户在做别的事 | 输出必须**一眼看懂**，不能要求读代码 |
| **时间** | 会话可以是小时级 | 单次交互通常 **10 秒 ~ 3 分钟** | 长任务要有"我可以先走开"的进度感 |
| **焦点** | 用户主动切过去 | 用户**不想被打断**（`noFocusSteal` 已是设置项） | 抢焦点是头号体验事故 |
| **输入** | 键盘打字为主 | **抓选区**（`Alt+Shift+Space`）是主入口 | 抓取质量决定成败 |
| **空间** | 960px+ 可用 | 360×480，**文字必须极度精简** | 长文档输出是**反模式** |
| **持久** | 会话文件是资产 | 用户不该感知"文件在哪" | 存储细节要藏起来 |

**这最后一条直接否掉了你的「不做文件更改」设想**，见 §4。

## 3. 可以删掉什么：code 功能 vs 文件能力

你说"去掉 code 功能"，这个直觉需要**拆成两半**，因为它们是不同的东西：

### 3.1 该删的：代码**工作台**能力（pi-web 的重型部分）

| 能力 | 删掉的理由 | 判断 |
|---|---|---|
| Git / worktree 集成 | 悬浮球里切 git 分支是荒谬的 | ✅ **删** |
| 文件树浏览（`FileExplorer`） | 360px 放不下树，且用户在做别的事 | ✅ **删** |
| 代码高亮 / ANSI / Mermaid | 小窗里没有人会读 200 行代码 | ✅ **删**（保留行内 code 样式即可） |
| 会话分支导航（`BranchNavigator`） | 树状导航需要空间与专注度 | ✅ **删** |
| Provider / 插件 / 技能配置面板 | 配置类 UI 属工作台职责，应引导去 pi-web 或 CLI | ✅ **删**（或只留一个"打开配置"跳转） |
| 项目信任对话框（`ProjectTrustDialog`） | 因为 minipi 不需要用户选任意项目目录 | ✅ **删**（见 §4.2） |
| 子代理体系 | 复杂度高，与"轻"冲突 | ✅ **删** |
| 文件上传 / 图片附件 | 悬浮球不做上传 | 🟡 暂缓 |

**这一半删掉，你们能省掉 pi-web 约 70% 的复杂度。** 这是对的，继续。

### 3.2 不该删的：**文件读写**能力

这是我要拦你一下的地方。

「去掉 code 功能」≠「去掉文件能力」。**Pi 内核的工具是 11 个内置工具**：

```
bash.ts  edit.ts  find.ts  grep.ts  ls.ts  powershell.ts  read.ts  write.ts ...
```

**没有一个是"编程专用"的。** `read`/`write` 是通用文件能力，`grep`/`find`/`ls` 是通用检索能力。
把它们当成"code 功能"是个误判。

**删掉 `write` 会发生什么？**

用户说：「帮我把这段整理成一份纪要」→ 模型只能在对话里吐一段文字 → 用户**手动复制**到 Word 里。
用户说：「把这个目录里的三份 PDF 要点汇总」→ **做不到**。
用户说：「把刚才的回答存成文件」→ **做不到**。

**这就是"又一个聊天框"**，而且是一个连 Ctrl+C 都要用户自己按的聊天框。

## 4. ❌ 最关键的一节：为什么「不做本地文件更改」这条要否掉

### 4.1 三个致命问题

**① 它消灭了 minipi 存在的理由**

Pi 的核心竞争力就是**能动手**。一个不能动手的 Pi，在 ChatGPT / Claude / 豆包 / Kimi 的包围下**没有任何差异化**。
这些产品聊天都免费，而且模型可能更强。你们唯一的护城河是「它在你桌面里，且能真的做事」。

**② 你说的"chat 模式"其实就是现有的 `speed` 场景**

这是好消息也是坏消息：

```js
speed: {
  toolAllowlist: [],
  noTools: "all",              // ← 已经是纯 chat
  sessionManagerMode: "memory", // ← 已经是不落盘
  description: "随手一问：概念、报错、翻译、改写。无工具可用、不落盘。",
}
```

**你们已经实现了「纯 chat + 不落盘」**（`speed` 场景）。所以"只做 chat"不是新设计，
而是**把产品砍到只剩三档场景里最浅的一档**。这显然不是你想要的产品。

**③ 它和你的第二诉求自相矛盾**

你同一句话里说了两件事：
- 「只做成 chat 模式，不做本地文件的更改」
- 「可以根据对话生成文档、表格、PPT 等办公文档」

**生成文档 = 写文件。** docx / xlsx / pptx 都是磁盘上的文件。
你不可能一边禁止写文件，一边生成办公文档。**这两条只能选一条。**

### 4.2 我的建议：不是「不做文件」，而是「**换个地方做文件**」

真正的问题**不是"该不该写文件"，而是"该往哪里写"**。

pi-web 的模型是：用户**显式选一个工作目录** → agent 在该目录里读写 → 需要 `ProjectTrustDialog` 确认信任 → 文件树/`allowed-roots.ts`/`path-security.ts` 一整套边界逻辑。

minipi 应该换一个模型：**用户永远不选目录，minipi 只有一个沙箱。**

| | pi-web | minipi（建议） |
|---|---|---|
| 工作目录 | 用户选任意项目 | **固定 `~/.minipi/workspace/`**，用户不感知 |
| 信任确认 | 每次新目录要弹信任框 | **不需要**（只有这一个目录，开机即信任） |
| 越界风险 | `..` / 绝对路径 / 符号链接逃逸 | **物理上无处可逃**（沙箱是唯一 cwd） |
| 文件树 UI | 必须有 | **不需要**（用户不选目录，自然不需要树） |
| 复杂度 | 高（`allowed-roots` + `path-security` + `project-trust`） | **低**（一个 JSDoc 约束 + 一次 `realpath` 校验） |

**这一个改动，同时满足了你两个诉求**：
- ✅ 用户**感觉不到**"本地文件被改了"——他从来没指定过任何目录，minipi 只碰自己的抽屉
- ✅ 办公文档生成**有了落点**——写进 `~/.minipi/workspace/`，生成完弹一个"打开 / 另存为"

而且它**比 pi-web 更安全**，因为攻击面从"任意目录"收缩到"一个目录"。
你现有的 `work` 场景已经是这个思路的雏形（`cwdTemplate: "~/.minipi/work"`），只是还不够。

### 4.3 ⚠️ 必须补的一个洞

`work` 场景当前是 `toolAllowlist: [read, write, edit, grep, find, ls, bash, powershell]`——
**`bash` 能 `cd /` 然后写任何地方**。沙箱对 `bash` 是**无效**的。

所以「沙箱」这个承诺，需要一条明确的执行规则：

> **只有 `work` 场景开 `bash`/`powershell`，且被 `tool_call` 闸门（M4）拦截任何路径逃逸的命令；
> 默认场景（`speed`/`study`）**不开 bash**。**

并且 `study` 场景当前没有 `edit`、没有 `bash`——**这个设计是对的，应该推广成默认心智**。

## 5. 你的核心担忧：chat 模式会不会太简单？

**会。如果只是 chat，一定太简单。** 你的担忧是对的。

但解法不是"加更多聊天功能"，而是**做"轻产出"**——让每次对话都有一个**可以带走的东西**。

### 5.1 办公文档生成该怎么做（这是关键设计）

先说一个**必须避开的技术陷阱**：

> ❌ **不要让模型直接生成 docx/xlsx/pptx。**
> 这些是 ZIP 容器格式，模型逐字节写必然损坏。而且成本高、不可控、无法校验。

✅ **正确做法：模板 + 代码填充 + 模型只出结构化内容。**

```
用户：「把刚才聊的整理成一份周报」
  ↓
[1] 主进程用一次 LLM 调用，让模型只输出**结构化 JSON**：
    { title, sections: [{ heading, bullets: [...] }], date }
  ↓
[2] 代码拿 JSON 去填模板（docx = python-docx / docxtemplater；xlsx = exceljs）
  ↓
[3] 落盘到 ~/.minipi/workspace/周报-2026-09-23.docx
  ↓
[4] 小窗弹一张极小卡片：「已生成 · 周报-09-23.docx」 + [打开] [另存为] [再改改]
```

**这个模式的好处**：
- 模型只做它擅长的（组织内容），代码做它可靠的（写二进制）
- 一键可测（模板渲染是确定性的，不靠模型）
- 成本可控（一次结构化输出，不是逐字节生成）
- **可校验**（JSON schema 错了立刻报错，不会产出坏文件）

我建议 **MVP 只做两个格式**，不要一上来三个都做：

| 格式 | 技术选型 | MVP | 理由 |
|---|---|---|---|
| **Markdown / .txt** | 纯文本 | ✅ **必做** | 零依赖，是所有格式的降级兜底 |
| **.docx** | `docx`（npm，纯 JS）或 python-docx | ✅ **必做** | 用户最常要的"文档" |
| **.xlsx** | `exceljs` | 🟡 第二优先 | 表格是"数据"不是"文章"，需要另一种交互（见 §5.2） |
| **.pptx** | `pptxgenjs` | 🔴 **推迟** | PPT 的价值在**视觉设计**，纯文字填充出来的 PPT 没人用。这个格式的期望值最高、最容易被骂 |

**关于 PPT 的坦白话**：用户说"生成个 PPT"，他**想象的是好看的 PPT**。
纯靠文字填充生成的 PPT，是"一页一条 bullet 的白底黑字"，交出去会挨骂。
**MVP 阶段不要做 PPT**，或者只做「Markdown 大纲 + 明确的"这是大纲，需要你在 PPT 里排版"提示」。
否则你会烧掉大量时间做出一个没人满意的功能。

### 5.2 表格的特殊性：它不是"产出"，是"操作"

表格和文档是**两种不同的交互**：

- 文档：**从无到有生成** → 一次性动作
- 表格：**对已有数据的处理** → 通常是"把这个转成表格"「筛选」「排序」「算一下」

所以 `xlsx` 的正确入口不是"生成一个表格"，而是：

- 「把这段数据转成表格」← 用户粘一段 CSV/文本
- 「把这个表里 X 列大于 Y 的挑出来」← 用户丢一个文件进来

**如果 MVP 阶段想省事，我建议先不做 xlsx**，改成「把数据渲染成**可复制的 Markdown 表格**」——
用户粘进 Excel 就自动分列。**零代码、零风险、体验其实不差**。等 M5 之后再上真 xlsx。

### 5.3 真正的差异化：不是"能生成文档"，是「**随手产出**」

这是我最想让你看到的一点。

「能生成文档」本身**不是差异化**——WPS AI、豆包、Kimi、ChatGPT 都能，而且做得比你们好。

minipi 的差异化应该是这个**动作链**：

```
你在写邮件 / 看报告 / 读论文
   ↓ 选中一段文字
   Alt+Shift+Space         ← 0.3 秒，不打断你
   ↓
悬浮球亮起「已抓 37 字」
   ↓ 打字：「总结成三条」
   ↓
3 秒后，球上出现一个小卡片
   ↓ 点一下
产出物已经落在 ~/.minipi/workspace/，且弹「打开」
```

**竞品要你：切窗口 → 找输入框 → 粘贴 → 打字 → 复制结果 → 切回来 → 粘贴。**
**minipi 要你：选中 + 一个热键 + 一句话。**

**差的是"步骤数"，不是"能力"。** 这才是移动端产品该有的思路——不是在功能上比别人多，而是在**摩擦上比别人少**。

所以我的建议是：**MVP 的重心不要放在"多支持几个格式"，而要放在"让抓选区 → 产出"这条链路快到 5 秒内完成"。**
一个能 5 秒内把选中文字变成文件的产品，比一个支持 5 种格式但要切窗口的产品，有价值得多。

## 6. TypeSafe / Jev 该用在哪（结论：**不在生成侧，在判断侧**）

我读了 TypeSafe 的实际文档，有一条硬事实必须澄清：

> `System One models do not write replies, produce code, or generate explanations of their reasoning.`
> —— [docs.typesafe.ai/concepts/system-one](https://docs.typesafe.ai/concepts/system-one)

**Jev 不生成任何东西。** 它只返回**结构化判断**，三种原语：

| 原语 | 问什么 | 返回 | minipi 里的用法 |
|---|---|---|---|
| **Choice** | 从定义好的集合里选 | 选项 + 概率分布 | 「这条输入属于哪类意图：改写 / 翻译 / 总结 / 生成文档 / 改代码 / **都不像**」 |
| **Score** | 沿有序维度打分 | 分数 + 各档概率 | 「这条回答的冗长度 0–4」（决定要不要折叠）/「这个操作的危险度」 |
| **Noul** | 是/否 | 是概率 | 「这条输入是不是在要求**写入文件**？」 |

### 6.1 ⚠️ 一个必须纠正的定位

`docs/minipi-plan.md` 里把 M5 定为"判定层"，**但 minipi 当前只有 3 个场景（speed/study/work）**。

如果场景是**用户手动切**的，那 TypeSafe 判定层的价值就很有限——
**用户在 UI 上已经点了一个按钮，你再用 AI 猜他的意图，是浪费。**

TypeSafe 真正有价值的场景是：

1. **场景切换的"自动推荐"** —— 用户不选场景，输入内容由 Jev 判断「这更像随手一问还是要动文件」，然后自动切。
   这是 Choice 的完美用例（含 `都不像` 兜底）。
2. **产出物格式判断** —— 用户说"整理一下"，Jev 判断他想要 Markdown / docx / 表格。
3. **回答冗长度自适应** —— 小窗空间有限，Jev 给 Score 决定折叠还是展开。
4. **危险操作预判** —— 配合 M4 闸门，Noul 先判一次"这是不是要动文件"，减少弹卡打扰。

**建议**：M5 的定位从"判定层"改成「**场景/意图路由器**」，且**必须晚于 M4**（因为它要消费闸门的信号）。
这也印证了我上一轮报告里的建议——**M4 应该排在 M3 前面**。

### 6.2 一条硬约束

Jev **只接受文本**（`Images, audio, and video are not supported (yet)`）。
所以抓选区的**图片场景用不了 Jev**，只有文本可以。这要写进设计。

## 7. 最终建议的能力边界

### 7.1 MVP 能力清单（建议）

| 层 | 能力 | 状态 |
|---|---|---|
| **输入** | `Alt+Space` 唤起 / `Alt+Shift+Space` 抓选区 | ✅ 已有 |
| **对话** | 流式问答、三场景、`Esc` 收起、位置记忆 | ✅ 已有（M1） |
| **产出** | **Markdown / txt / docx 三种落盘** + 打开/另存为卡片 | 🔴 **新增（这是关键增量）** |
| **安全** | `tool_call` 审批闸门 + 沙箱 cwd + 拒绝语义 | 🔴 M4 |
| **体验** | 七级长任务状态、工具卡、超时拒绝 | 🔴 M3 |
| **智能** | Jev 场景/意图路由（可选、可关） | ⚪ M5 |

### 7.2 明确不做（建议写进文档，防止范围蔓延）

- ❌ Git / worktree / 分支树
- ❌ 文件树浏览器 / 代码高亮 / Mermaid
- ❌ Provider / 插件 / 技能配置面板（引导去 pi-web）
- ❌ 子代理体系
- ❌ 用户自选工作目录（**这是与 pi-web 最本质的分野**）
- 🟡 PPT 生成（推迟，理由见 §5.1）
- 🟡 xlsx 生成（先用 Markdown 表格兜底）

### 7.3 与 pi-web 的关系：**不是竞品，是上下游**

这一点建议写进产品定位：

> **pi-web 做「重活」，minipi 做「轻活」，共用同一份 `~/.pi` 数据与模型配置。**
>
> 在 minipi 里随手问、随手产出的小东西，落在 `~/.minipi/workspace/`；
> 需要认真改代码、看 diff、切分支时，引导用户去 pi-web。

这反而让两个产品**互相导流**而不是互相蚕食。

## 9. 一句话总结

> **别把 minipi 做成"小号的 pi-web"，也别做成"又一个聊天框"。**
> **把它做成「选中 → 一句话 → 得到一个文件」的 5 秒通道。**
> 文件**要写**，但只写进它自己的抽屉；办公文档**要做**，但只做文档和表格，别碰 PPT。
