## 六、三条必须带进后续开发的实测约束

这三条是 spike 花钱花时间换来的，**不照做会返工**：

1. **M1/M3 不得依赖 `resize` 事件做「变形完成」信号**——实测 `setBounds` 后 2 秒内 `resize` 未触发，且尺寸有 1px 圆整偏差（360→361、960→961）。改用 `did-finish-load` / 自绘帧回执 / 直接轮询 `getBounds()`。
2. **`backgroundThrottling: false` 必须在构造期设**——运行期 `setBackgroundThrottling()` 的结论**不可判定**（测量窗口未被真正遮挡）。遮挡节流实测很凶：`bt=false` rAF 跑 181（60/s），`bt=true` 掉到 **0**。
3. **用自绘伪最大化**——`maximize()` 虽然能铺满且保持透明，但 `isMaximized()` 返回 `false`、`unmaximize()` 回不去。语义不完整，不能靠它。

## 七、我的建议（要不要按这个顺序做）

**建议顺序：M2 加固 → M4 审批闸门 → M3 长任务 → 托盘/自启 → QA 复验**

理由：**M4 提前到 M3 前面**。原来的顺序是先做长任务体验再做审批闸门，但审批闸门是**安全底线**——
在它落地前，`work` 场景下 Pi 可以不经确认改文件、跑命令。而 M3 的「工具卡」和 M4 的「审批卡」
在 UI 上是同一个组件族，先做 M4 能顺手把 M3 的卡片基建一起打好，反而省工。

**砍掉建议**：MVP 阶段 M6 只保留「托盘 + 开机自启」，多屏 / 主题 / 全屏隐藏推迟。
