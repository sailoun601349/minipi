## 1. 架构约束速览

### 1.1 零构建单文件意味着什么

`src/renderer/index.html` 是**自包含单文件**：

```html
<head>
  <style> /* 全部 CSS 内联，约 1275 行 */ </style>
</head>
<body data-mode="ball">
  <svg id="iconSprite">…</svg>   <!-- 图标 sprite，内联 symbol -->
  …
  <script type="module"> /* 全部 JS 内联，约 5900 行 */ </script>
</body>
```

文件头部的约束注释（`src/renderer/index.html:9-21`）是产品负责人已拍板的红线：**零外部依赖、纯 ESM、无 `link rel=stylesheet`、无 `script src=`、无 `@import`、无 CDN、无 fetch/XHR/WebSocket**。

因此：

| 想做的事 | 为什么不行 | 替代做法 |
|---|---|---|
| 引入 Tailwind / Bootstrap | 外链 stylesheet → 破坏零外部子资源；且 `qa-future-ui` H1 判 FAIL | 手写内联 CSS，复制 §3.4 的骨架模板 |
| 引入 Sass / Less / PostCSS | 需要构建步骤；`file://` 下 ESM 外链会被 CORS 拦（文件头注释已记录） | 用 CSS 变量 + `color-mix()` 组合代替预处理器 |
| 引入 React / Vue | 需要打包；且渲染层已有 store + rAF 渲染驱动（`src/renderer/index.html:1788` 起） | 沿用现有 `el()` / `store` / `renderChrome()` / `renderViews()` |
| 拆 CSS 到独立文件 | 同上 | 全部内联进同一个 `<style>` |
| 引外部字体 | H4 判 `@font-face` FAIL | `--sans` / `--mono` 系统字体栈 |
| 加 `z-index` 层级工具类 | 现状层级散落（`z-index:120` / `500` / `51`），未形成层级表 | 按 §3.4 模板就近声明，不做全局层级系统 |

> **一句话**：minipi 的渲染层是一个**手工维护的组件库**，不是工程化的组件库。所有"复用"能力都由 CSS 变量 + 复制粘贴骨架提供。

### 1.2 新增样式往哪写

**位置**：全部写进 `src/renderer/index.html` 的 `<style>` 块内（`</style>` 在第 1300 行）。

**分区约定**：`<style>` 块内已按功能分成 12 个编号分区，每区用统一注释头：

```css
/* ==========================================================================
   4. 通用控件
   ========================================================================== */
```

新增样式有两种归处：

| 情形 | 放哪 | 例子 |
|---|---|---|
| 与既有组件同族 | 紧跟该组件的既有规则之后，**不新开分区** | 新增 `.chip--pdf` → 紧跟 `.chip--md` 之后 |
| 全新组件族 | 追加到编号分区的末尾，**新开一个编号分区**（编号续接，不复用旧号） | 新增「任务看板」→ 新开 `13. 任务看板` |
| 令牌 | **只能**写进四个令牌块（§2.2） | — |

> **分区编号只增不改**：既有 1–12 区的编号与标题**冻结**。新分区从 13 起顺延；废弃的分区**保留编号并标注「（已废弃）」**，不重排 —— 重排会让"按行号施工"的文档（`04-落地映射.md`）全部失效。

**分区内部三段式**（新组件族照此写）：

```css
/* ==========================================================================
   13. 任务看板（Task Board）
   --------------------------------------------------------------------------
   一句话说清：这块干什么、贴在哪个层级、360 宽下有什么硬约束。
   ========================================================================== */
/* ① 容器：卡片面 + 1px 描边 + 顶边内高光（浮起） */
.taskboard{ … }
/* ② 元素：块内子件 */
.taskboard__row{ … }
/* ③ 状态修饰：--degraded / --running 等 */
.taskboard--degraded{ … }
```

### 1.3 HTML / CSS / JS 的组织顺序约定

单文件里三者的**物理位置**本身就是约定，改动时不要挪动：

| 顺序 | 内容 | 位置 | 约定 |
|---|---|---|---|
| 1 | `<style>` 全部 CSS | `<head>` 内，第 23–1300 行 | 令牌块在最前（§2.1），组件分区在后 |
| 2 | `<body>` 静态外壳 | 第 1302 行起 | 三个形态容器**常驻 DOM**，切换形态只改 `hidden`（不重建 DOM） |
| 3 | `<svg id="iconSprite">` | `<body>` 顶部，第 1306 行附近 | **不能加 `hidden`**：`display:none` 的子树上部分浏览器解析不到 `<symbol>`/`<linearGradient>`；用 `width:0;height:0;overflow:hidden` |
| 4 | `<script type="module">` | 文件末尾，第 1788 行起 | 契约常量镜像 → 工具函数 → store → 渲染函数 → 事件绑定 |

**CSS 内部再分三层**，从上到下：

```
① 令牌块（4 处）      ← 唯一允许出现颜色字面量的地方
② 基础重置            ← *、html/body、focus-visible、reduced-motion、keyframes
③ 组件分区（12 区）    ← 零 hex / 零 rgba() / 零 transform:scale()
```

> **JS 里也不许写死颜色**：`qa-theme.mjs` 的 `[B2]` 组会扫 `<script>` 里的 `#hex` / `rgba()` 字面量（白名单只有 `iconMarkup()` 里的 `stroke="#000"`——那是拼给 CSS mask 的 data-URI，只取 alpha 通道）。JS 里设颜色只能写 `el.style.color = 'var(--danger-ink)'`（`qa-theme.mjs:113` 有对应断言）。

## 2. 令牌体系规范

> **本章是全文最重要的部分。** 令牌体系是 minipi 前端唯一的主题机制 —— 没有第二个 theme provider，没有 CSS-in-JS，没有 `data-theme` 之外的第三套覆盖路径。**令牌写错 = 主题坏掉，而主题坏掉不会报错，只会静默。**

### 2.1 四块结构与优先级

渲染层的四个令牌块（`src/renderer/index.html:28-197`），**优先级从低到高**：

```
① :root { ... }                                   L28-79    暗色兜底（永远存在的底座）
        ↓ 被 ② 覆盖
② @media (prefers-color-scheme: light) { :root { ... } }
                                                  L83-121  跟随系统（Electron 的 nativeTheme.themeSource 直接改这个媒体特性 → 零 JS、零 IPC、零首帧闪烁）
        ↓ 被 ③ 覆盖
③ html[data-theme="light"] { ... }                L124-160 手动强制：浅色（设置页 / mock / 截图预览）
        ↓ 被 ④ 覆盖
④ html[data-theme="dark"]  { ... }                L161-197 手动强制：暗色
```

**四块的职责**：

| 块 | 作用 | 谁在用 |
|---|---|---|
| ① `:root` | 暗色兜底 + **全部主题无关令牌**（圆角、字体、`--fx-grid-size`、`--fx-grid`） | 所有场景 |
| ② `@media light` | 跟随系统时的浅色值 | 真机默认（`theme: system`） |
| ③ `html[data-theme="light"]` | 手动强制浅色 | 设置页选"浅色"、mock 预览、截图脚本 |
| ④ `html[data-theme="dark"]` | 手动强制暗色 | 设置页选"暗色"、mock 预览、截图脚本 |

> **② 与 ③④ 的值必须逐字相同**：`qa-future-ui.mjs` 的 A2 组断言 `--fx-*` / `--ball-*` 令牌名集合在四块间**完全一致**；A4 组进一步断言既有 T1 令牌在四块的**值**与规格文档一致。

**优先级链的实战后果**：

- 用户选"跟随系统"（`system`）→ 渲染层**不设** `data-theme` → 只有 ① ② 生效。
- 用户选"浅色/暗色"→ 渲染层设 `html[data-theme="light"|"dark"]` → ③ ④ 生效，**② 仍可能生效**（系统是浅色时），但 ③ ④ 优先级更高，覆盖 ②。

### 2.2 「新增令牌四步法」

> **四步，一步都不能省。** 漏第 3 步 = 门禁红；漏第 4 步 = 门禁红。

#### 第 1 步：判定「要不要新令牌」

按 §2.3 的判据表做一次判断。**判据不通过就不要加** —— 已有令牌能表达的语义一律复用。

**检查方法**：

```bash
# 在 :root 块里 grep 候选语义是否已有近似令牌
grep -n -- "--surface-2\|--border-strong\|--fx-lit-top" src/renderer/index.html | head
```

#### 第 2 步：定名（前缀语义）

按 §2.3 的前缀表选前缀。**新命名空间不得随意扩张** —— 已有的两个新命名空间是 `--fx-*`（效果层）与 `--ball-*`（球体光影）。

**检查方法**：

```bash
# 新令牌名必须落在已批准的命名空间内。
# ⚠ 必须锚定行首（^\s+--）只匹配**令牌定义行**；
#   若写成 `grep -o -- "--[a-z0-9-]*:"` 会连 CSS 修饰类（.btn--ghost:）一起命中，产生假阳性。
grep -oE '^\s+--[a-z0-9-]+:' src/renderer/index.html | tr -d ' :' | sort -u \
  | grep -vE '^--(fx|ball|bg|surface|composer|border|divider|text|muted|accent|danger|success|warn|violet|shadow|overlay|code|diff|radius|mono|sans)'
# 期望输出为空（空 = 没有野生命名空间）。实测当前为空。
```

> 注意白名单里**不含** `--on-accent` / `--text-1` 之类 —— 但 `--on-accent` 是既有合法令牌，
> 若上面的命令把它报出来，先核对 `src/renderer/index.html` 里是否真有该定义（本项目实测 `--on-accent` 存在于四块）。

#### 第 3 步：写入令牌块

**分支 A —— 主题相关（颜色、阴影值）**：**四处全写**。

| 块 | 写什么值 |
|---|---|
| ① `:root` | 暗色值 |
| ② `@media light` 的 `:root` | 浅色值 |
| ③ `html[data-theme="light"]` | **与 ② 逐字相同**的浅色值 |
| ④ `html[data-theme="dark"]` | **与 ① 逐字相同**的暗色值 |

**分支 B —— 主题无关（圆角、尺寸、复合值）**：**只在 ① `:root` 定义一次**。

判据是"这个值是否引用了颜色令牌"：
- **是** → 主题无关（引用会跟着颜色令牌自动变）→ 只写 ①。
- **否** → 主题相关 → 四处全写。

现有两个范例：`--fx-grid-size:24px`（纯尺寸，主题无关）、`--fx-grid`（`repeating-linear-gradient(...)` 内部引用 `var(--fx-grid-line)`，主题无关）。

> `qa-future-ui.mjs` 的 A3 组**强制**这个分支：断言 `--fx-grid-size` / `--fx-grid` 只在 `:root` 出现一次，且内部**不得**含硬编码色值（`#hex` / `rgba()`）——只能 `var()` 引用颜色令牌。

**检查方法**（写完立刻跑）：

```bash
node scripts/qa-future-ui.mjs
# 关注 [A] 组：
#   A1 四块都定义了全部主题相关新令牌
#   A2 --fx-* / --ball-* 令牌名集合在四块完全一致
#   A3 主题无关令牌只在 :root 定义一次、内部无硬编码色值
#   A5 新令牌在四块都是有效值（非空 / 非 undefined / var() 引用可解析）
```

#### 第 4 步：接入消费者 + 生命周期登记

**新令牌必须有消费者。** 定义了却没人用的令牌 = 维护负债（四块都要维护），要删。

**检查方法**：

```bash
# 统计某个新令牌被消费的次数（= var(--xxx) 出现次数）
grep -c -- "var(--fx-lit-top" src/renderer/index.html

# 反向体检：列出定义了但零消费的令牌
node -e "
const fs=require('fs');const h=fs.readFileSync('src/renderer/index.html','utf8');
const defs=new Set([...h.matchAll(/(--[a-z0-9][a-z0-9-]*)\s*:\s*[^;]*;/g)].map(m=>m[1]));
const uses=new Set([...h.matchAll(/var\(\s*(--[a-z0-9-]+)/g)].map(m=>m[1]));
const orphan=[...defs].filter(t=>!uses.has(t)).filter(t=>/^--(fx|ball)-/.test(t));
console.log(orphan.length?('孤儿令牌: '+orphan.join(' ')):'无孤儿令牌');
"
```

> **实测输出**（2026-10-22，当前产品代码）：`孤儿令牌: --ball-ink --ball-logo-shadow`。
> 这两个确为孤儿 —— `--ball-ink` 是 π 实体色（由 SVG `fill="var(--ball-ink)"` 消费，脚本正则扫不到 `fill="var(...)"`），
> `--ball-logo-shadow` 供 π 柔影（当前 SVG 未接）。
> ⚠ **脚本的已知局限**：它只扫 CSS 块里的 `var(--token)`，扫不到 SVG 属性的 `fill="var(--token)"` / `stop-color`，
> 所以**不能只信脚本**，必须人工确认一次。

### 2.3 什么时候新增、什么时候复用

| 情形 | 判定 | 动作 |
|---|---|---|
| 语义与既有令牌**完全一致**（同一个视觉角色、换一批组件也要用） | 复用 | 直接 `var(--已有令牌)`，**不要**为局部场景造同义令牌 |
| 语义一致但**出现频率低 / 组件私有** | 复用 | 组件私有色差用 `color-mix(in srgb, var(--已有) N%, transparent)` 表达 |
| 语义是**新的视觉角色**（既有令牌无法表达） | 新增 | 走 §2.2 四步法 |
| 只是**数值微调**（如 8% → 10%） | 复用 + 覆盖 | 优先 `color-mix()`；确需覆盖作用域才新增修饰类，且**颜色仍来自令牌** |
| 想加一个新的**色相**（红/黄/绿/紫之外） | **默认禁止** | 现有一整套状态色（`--danger` / `--warn` / `--success` / `--violet` / `--accent`）已覆盖需求；新增色相会让"单点 accent"破功 |
| 想加**透明度变体**（如 `--accent-30`） | **默认禁止** | 用 `color-mix(in srgb, var(--accent) 30%, transparent)`；不新建 alpha 令牌（`qa-future-ui` / 规格 §6 规则 2） |

**判据一句话**：**令牌是语义，不是数值。** 一个令牌名如果只描述"多浅/多深"而不是"这是什么角色"，就该用 `color-mix()` 表达。

### 2.4 命名规范

#### 前缀语义表

| 前缀 | 数量 | 语义 | 归属 | 写在哪 |
|---|---|---|---|---|
| `--fx-*` | 10 | **效果层**：光影、纹理、描边等"怎么画"的信息，不指明"画在什么上" | 视觉方案 | 四处（除 `--fx-grid-size` / `--fx-grid`） |
| `--ball-*` | 23 | **球体光影**：48×48 悬浮球的专属明度阶梯与 π 浮凸 | 球 | 四处（除无） |
| 既有 `--*`（T1 底座） | 38 | **结构语义**：表面、文字、主色、状态、代码、diff | 底座 | 四处 |
| `--radius*` / `--mono` / `--sans` | 9 | 圆角（7 个）/ 字体栈（2 个） | 非颜色 | 只在 ① `:root` |

#### 命名规则

| 规则 | 反例 | 正例 |
|---|---|---|
| 全小写 + 连字符 | `--fx-LitTop` | `--fx-lit-top` |
| 语义名词，**不含数值** | `--fx-shade-42` | `--fx-shade-bottom` |
| 同一族用统一后缀 | `--fx-shade-a` / `--fx-shade-b` | `--fx-shade-bottom` / `--fx-shade-inset` |
| 布尔状态用成对修饰（`--x` / `--x-hover`） | `--hover-border-color` | `--ball-hover-border`（成对是 `--ball-border` / `--ball-hover-border`） |
| 纯装饰、只服务一个组件族时，仍走 `--fx-*` 而非自定义前缀 | `--task-` | `--fx-edge-hair`（复用） |

**什么该叫 / 什么不该叫**：

| 该叫 | 不该叫 | 理由 |
|---|---|---|
| `--fx-glow-accent`（accent 色的极弱晕） | `--fx-blue-glow` | 令牌名要跟**令牌**绑，不跟当前色相绑；换主题后 `--accent` 会变，名字不能变 |
| `--ball-pi-hi`（π 的亮端） | `--ball-white-shine` | π 是品牌实体，`--ball-pi-*` 三端是**一组**，必须成套出现 |
| `--fx-grid-line-2`（网格主轴线） | `--fx-grid-bold` | "2"指层级（主轴），不是粗细 |

> **成套规则**：`--ball-pi-hi` / `--ball-pi-mid` / `--ball-pi-lo` 是**一组亮度阶梯**，任何一块的取值变化都要三块一起复核（§3.3）。

### 2.5 令牌生命周期

**一条令牌的一生**：

```
需求 → §2.3 判据（复用还是新增）→ §2.2 四步法 → 被组件消费
                                                      ↓
                              组件下线 / 语义变更 → 消费者归零 → 删令牌（四处一起删）
```

**硬规则**：

1. **定义了却零消费者 = 删。** 理由：令牌要维护四处，任何一处漏改就是 bug；没人用的令牌是纯负债。
2. **删除必须四处同步删。** 只删一处 → 另三块残留孤儿令牌（`qa-future-ui` A2 会发现集合不一致）。
3. **改值不改名。** 改名 = 新令牌（旧的按第 1 条删）—— 改名的中间态会让 `var()` 解析失败。
4. **既有 T1 令牌的值不可改**（`--ball-ink` 是唯一已获批的例外，值见 `02-令牌规格.md` §1.6 注）。`qa-future-ui` A4 组逐条比对，任何既有令牌被改动即 FAIL。

**判定命令**（孤儿检查 / 覆盖率）见 §2.2 第 4 步。

**新增到 `ui-optimization/future-ui/02-令牌规格.md`**：门禁 `qa-future-ui.mjs` 的**令牌名单是从规格 Markdown 的表格里运行时解析出来的**（`scripts/qa-future-ui.mjs:65-74`），不硬编码。所以：

> **新增令牌 = 改代码 + 改规格文档**，两者缺一不可。只改代码 → 门禁不认识这个令牌（A1/A5 覆盖不到，且未来某次解析失败会 `fatal`）。只改文档不改代码 → A1 报"四块缺失"。

### 2.6 硬编码禁令与 `color-mix()` 边界

| 位置 | 允许 | 禁止 |
|---|---|---|
| 四个令牌块内 | 任意 hex / `rgba()` / 阴影值 | — |
| 组件区（`<style>` 内令牌块之外） | `var(--令牌)`、`color-mix(in srgb, var(--令牌) N%, transparent)` | **任何** `#hex`、`rgb()`、`rgba()` 字面量 |
| `<script>` 内 | `var(--令牌)` 字符串 | `#hex` / `rgba()` 字面量（白名单只有 `iconMarkup()` 的 `stroke="#000"`） |

**`color-mix()` 的允许边界**：

| 用法 | 判定 |
|---|---|
| `color-mix(in srgb, var(--accent) 14%, transparent)` | ✅ 允许 —— 从既有令牌派生透明度 |
| `color-mix(in srgb, var(--danger) 50%, transparent)` | ✅ 允许 —— 状态色变体 |
| `color-mix(in srgb, var(--text) 2%, transparent)` | ✅ 允许 —— 极弱面底 |
| `color-mix(in srgb, #4c9aff 20%, transparent)` | ❌ 禁止 —— 里面是硬编码色，等价绕过令牌 |
| `color-mix(in srgb, var(--accent) 20%, var(--surface))` | ✅ 允许 —— 两端都是令牌 |
| `color-mix(in srgb, var(--accent) 20%, #000)` | ❌ 禁止 —— 一端是硬编码色 |

> **为什么允许 `color-mix` 而不是新建 alpha 令牌**：alpha 令牌是"数值"不是"语义"，会随主题错配（暗色主题的 14% 白在浅色主题下就变味）。`color-mix` 永远从当前主题的令牌派生，天然正确。

**门禁**：`qa-theme.mjs` 的 `[B]` 组（CSS）与 `[B2]` 组（JS）、`qa-future-ui.mjs` 的 `[B]` 组（三条：hex / rgb() / 组件区重新定义 `--fx-*`/`--ball-*`）。

### 2.7 双主题同构

**同构的定义**：同一套 DOM、同一套类名、同一套 CSS 规则结构，只靠**换令牌值**就同时成立暗色与浅色。

**怎么判定同构**：

| 检查 | 命令 / 方法 |
|---|---|
| 两主题的类名集合一致 | 浅色/暗色**不写任何条件选择器**：`html[data-theme="light"] .foo{...}` 视为违规（除非是结构性差异，且要写明理由） |
| 令牌覆盖完整 | `node scripts/qa-theme.mjs` 的 `[D]` 组（切换真的改变计算样式）+ `qa-future-ui` A1/A2 |
| 语义方向一致 | 暗色"光 = 加白、影 = 加黑"；浅色"光 = 加白（更强）、影 = 加墨（更弱）" —— 见下表 |
| 对比度达标 | `qa-theme` 的 `[F]` 组：正文 ≥4.5:1、次级正文 ≥4.5:1、辅助文字 ≥3.0:1（对 `--surface` 实算） |

**浅色主题的关键调整只有一条**：

| 手法 | 暗色 | 浅色 | 令牌 |
|---|---|---|---|
| 顶边高光 | 弱（0.07） | 强（0.85，底已经亮） | `--fx-lit-top` |
| 底部内暗 | 强（0.42） | 弱（墨 0.10） | `--fx-shade-bottom` |
| 主色 | `#4c9aff`（亮蓝，暗底上更跳） | `#1f6feb`（深蓝，白底上更稳） | `--accent` |
| 主色文字 | `#9cc7ff` | `#1557c0` | `--accent-ink` |

> 这就是 `--fx-lit-*` / `--fx-shade-*` 必须**成对出现**的原因：一个令牌在两主题下的"物理含义"不同 —— 浅色主题里"加白"是"更亮"，暗色主题里"加白"是"更柔"。

## 3. 组件实现规范

### 3.1 透明窗裁剪铁律（窗口几何 == 卡片几何）

#### 原理

minipi 的窗口是**透明窗**（Electron `transparent: true`），**窗口矩形 == 卡片矩形**：

| 形态 | 窗口尺寸 | 卡片几何 |
|---|---|---|
| 球 | 48×48 | `.ball` 48×48（`border-radius:50%`） |
| 小窗 | 360×480 | `.mini` 铺满窗口，`border-radius:var(--radius-xl)` |
| 大窗 | 960×680 | `.full` 铺满窗口 |

Electron 的裁切边界 = **窗口矩形**。任何**外扩**的绘制（`box-shadow` 的 blur/spread、`filter: drop-shadow()`、`text-shadow`、外发光）溢出到矩形外的透明区，在深色壁纸上就显示为**一圈淡淡的方形边**。

> **用户已投诉两次**（`03-组件规格.md` 裁剪坑 1/2；`04-落地映射.md` §7 把"用户第三次投诉淡边"列为最高风险）。

**为什么 `inset` 永远安全**：`inset` 把阴影画在元素**自己的矩形内部**，几何上不可能越界。

#### 门禁口径

`qa-future-ui.mjs` 的 `[C]` 组：

- **C1** —— 选择器命中 `.ball` / `.ball--sphere` / `.mini` / `.full` 时，`box-shadow` 的**每一层**都必须含 `inset`。
- **C2** —— 全文（含 keyframes）**零** `transform: scale(...)`，任何值、任何选择器。
- **C3** —— 球/窗口元素上无 `drop-shadow` / `text-shadow`（π mark 内部的滤镜允许，但不得落在球壳上）。
- **D3** —— keyframes 里不得有外扩光环 `0 0 0 Npx`（N>0），只允许向内发光的替代 keyframes。

#### 正确写法

```css
/* ✅ 窗口根卡片：顶边 1px 内高光 = 浮起。零外扩。 */
.mini{
  background:var(--surface);
  border:1px solid var(--border-strong);
  border-radius:var(--radius-xl);
  box-shadow:inset 0 1px 0 var(--fx-lit-top);
  overflow:hidden;
}

/* ✅ 贴边浮层（popover / 能力菜单 / 命令面板）：也只用 inset */
.popmenu{
  background:var(--surface);
  border:1px solid var(--border-strong);
  border-radius:var(--radius-md);
  box-shadow:inset 0 1px 0 var(--fx-lit-top), inset 0 -8px 14px -10px var(--fx-shade-bottom);
}

/* ❌ 禁止：外扩阴影落在透明窗角区 = 一圈淡边 */
.mini{ box-shadow:0 18px 50px rgba(0,0,0,.5); }
```

**例外**：`--shadow-1` / `--shadow-2`（**外扩**阴影）**只允许**用在**窗口内部浮层**且**距窗口边缘 ≥40px** 的居中面板（命令面板、设置面板）。贴边浮层（能力菜单、导出 popover）一律改用 inset —— 现状 `src/renderer/index.html:1162-1192` 就是这么做的（`.popmenu` / `.capmenu` / `.cmdpanel` 全用 inset）。

> **判断口诀**：**离窗口边缘近 → 只用 inset；离得远且居中 → 才可外扩。** 拿不准就用 inset —— inset 永远不会错。

### 3.2 禁止 `transform: scale()`

#### 为什么

- 球态：48px 窗口里 `scale(1.06)` 被窗口边界裁掉 1.4px，**像被切了一刀**；`scale(.96)` 让球与 48px 窗口边缘出现 **0.7px 透明缝**（边缘发虚）。
- 通用：缩放会改变元素的**实际占位**，在 360 宽的小窗里让相邻元素挤压/换行。

#### 替代手法（只用这三个属性）

| 反馈 | 正确写法 | 现有范例 |
|---|---|---|
| hover | `border-color` + `background` | `.btn:hover{ background:var(--surface-3); color:var(--text); border-color:var(--border-strong); }`（`index.html:399`） |
| press | `inset box-shadow` 加深 | `.iconbtn:active{ transform:translateY(1px); box-shadow:inset 0 1px 3px color-mix(in srgb, var(--fx-shade-inset) 70%, transparent); }`（`index.html:1136`） |
| 球 press | 高光收缩 + 内暗加深 | `.ball--sphere:active{ box-shadow:inset 0 4px 8px -7px var(--ball-top-glow), inset 0 -7px 11px -8px var(--ball-inset-dark), inset 0 -4px 7px -6px var(--ball-rim); }`（`index.html:335-340`） |

> **`translateY(1px)` 是允许的** —— 它是位移不是缩放，不改变占位尺寸。`qa-future-ui` C2 只禁 `scale()`。
> **注意**：`transform:none !important`（`.ball--drag`，`index.html:299`）是**清掉宿主脚本可能注入的 transform** 的兜底，不要删。

### 3.3 π 品牌规则

> **规则**：π 必须**比气泡亮**。否则 π 读作「洞」（挖空）而不是「凸」（浮雕）。

**判据（机械）**：`qa-future-ui.mjs` 的 `[E]` 组：

- **E1** —— `--ball-pi-hi` / `--ball-pi-mid` / `--ball-pi-lo` 在规格中存在且暗/浅两块都有值。
- **E2** —— 暗色与浅色下，π 三端的 sRGB 相对亮度**都高于**气泡底色（`--accent` 与 `--accent-2` 的较大者）。
- **E3** —— `--ball-ink` 暗色相对亮度不低于 `#0b1220`（π 不是挖空的洞）。

**当前值（渲染层现状）**：

| 令牌 | 暗色 | 浅色 | 角色 |
|---|---|---|---|
| `--ball-bubble-hi` | `#5a9bf7` | `#4a90f0` | 气泡亮侧 |
| `--ball-bubble-lo` | `#123f7e` | `#0d47a6` | 气泡暗侧 |
| `--ball-pi-hi` | `#eaf4ff` | `#ffffff` | π 顶面亮 |
| `--ball-pi-mid` | `#c2dcff` | `#e2efff` | π 中段 |
| `--ball-pi-lo` | `#93c2f6` | `#b9d6f7` | π 底面（最暗端，**仍须亮过气泡**） |
| `--ball-ink` | `#0b1220` | `#1557c0` | π 前景墨色 |

**两主题语义统一**：暗色是「石墨仪器上的浅色浮雕」，浅色是「白瓷仪器上的深蓝浮雕」—— **方向一致（π 永远在气泡之上），实现不同（暗色加白、浅色加墨）**。

> ⚠ **不要**把 `--ball-ink` 改回近黑（`#0b0f14` 一类）：深色主题下会读作洞。E3 是硬断言。

**派生规则**：改 π 的任何一端时，**三端 + 气泡两端**要一起复核亮度关系；门禁 E2 会替你算，但只在 `--accent` / `--accent-2` 不变时可靠 —— 若同时改了主色，**必须自己重算**。

### 3.4 骨架模板

> ⚠ **以下 CSS 块是「模板」**，用来说明结构与取值口径。**实际实现以 `src/renderer/index.html` 里的现有代码为准** —— 那是唯一真源，模板与现状不一致时**以现状为准**（并在 §7 记录差异）。

#### 命名约定（BEM 风格）

```
block__element--modifier
```

| 段 | 写法 | 例子 |
|---|---|---|
| block | 组件族名，小写连字符 | `outcome` `approval` `toolcard` `popmenu` |

|---|---|---|

## 4. 图标规范

### 4.1 为什么聊天流里不能有 `<svg>`

**机械理由**：`scripts/qa-renderer-edge.mjs` 的 **C5** 组做 XSS 实测，判定口径是"**真实 DOM 解析后**存在 `script,iframe,svg,math,object,embed` 元素，或任意 `on*` 事件属性，或 `javascript:`/`data:` 链接"。它**分不清**我们的图标和载荷里的 `<svg onload>` —— 两者都是 `svg` 元素。

**后果**：一旦聊天流里出现 `<svg>` 节点，C5 判 **P0** —— 我们的图标被当成注入成功。

**规则**：

| 位置 | 允许 | 禁止 |
|---|---|---|
| 聊天流（`#miniBody` 子树） | `<span>` + CSS `mask-image` | **任何** `<svg>` 元素 |
| 脚本里生成图标 | `<span>` + mask | 生成裸 `<svg>` 节点 / `innerHTML = '...<svg...'` |
| 静态外壳（`<body>` 顶层） | sprite `<svg>` + `<use href="#i-x">` | — |

> `qa-future-ui.mjs` 的 `[G]` 组是**静态等价**的同一口径：G1（`#miniBody` 子树零 `<svg>`）、G2（脚本里不生成裸 `<svg>` 节点，只允许带 `xmlns` 的独立 SVG 文档字符串）、G3（不通过 `innerHTML` 注入 `<svg>`）、G4（`iconEl()` 不返回 svg 元素）。

### 4.2 `iconEl()` 的用法

`iconEl(name, size, cls)` 在 `src/renderer/index.html:2094-2101`：

```js
/**
 * 取一个图标（CSS mask 版）。
 * @param {string} name sprite 里的 symbol 名（不含 `i-` 前缀）
 * @param {number} [size] 边长（px）；不传则交给 CSS（`.ico` 16）
 * @param {string} [cls] 额外 class（如 `popmenu__i` / `chip__i`）
 * @returns {HTMLElement}
 */
function iconEl(name, size, cls) {
  const span = el('span', `${cls || 'ico'} ico-mask`);
  span.setAttribute('aria-hidden', 'true');
  if (size) { span.style.width = `${size}px`; span.style.height = `${size}px`; }
  const markup = iconMarkup(name);
  if (markup) span.style.setProperty('--ico', `url("data:image/svg+xml,${encodeURIComponent(markup)}")`);
  return span;
}
```

**用法**：

```js
// 在动态节点上挂图标（聊天流内安全）
const btn = el('button', 'btn btn--sm');
btn.appendChild(iconEl('copy', 14, 'btn__i'));   // name = sprite 里的 symbol 名（去掉 i- 前缀）
btn.appendChild(el('span', null, '复制'));
```

**配套 CSS**（`index.html:1148-1156`）：

```css
.ico-mask{
  display:inline-block; width:16px; height:16px; flex-shrink:0;
  background-color:currentColor;                              /* 颜色跟随文字色 */
  -webkit-mask-image:var(--ico); mask-image:var(--ico);
  -webkit-mask-repeat:no-repeat; mask-repeat:no-repeat;
  -webkit-mask-position:center; mask-position:center;
  -webkit-mask-size:contain; mask-size:contain;
}
```

**要点**：

| 要点 | 说明 |
|---|---|
| 颜色 | `background-color: currentColor` —— 图标自动跟随文字色，不需要为每个图标配颜色 |
| 尺寸 | 默认 16px；`.btn .ico` 是 14px；`.chip__i` 是 12px |
| 无障碍 | `aria-hidden="true"`（图标是装饰，语义由旁边的文字承担） |
| 源 | `iconMarkup(name)` 从 `<svg id="iconSprite">` 里的 `<symbol id="i-xxx">` 取 `innerHTML`，拼成独立 SVG 文档后 `encodeURIComponent` 成 data-URI |
| 零网络 | data-URI 内联，**零外部请求** |

**新图标要做什么**：在 `<svg id="iconSprite">` 里加一个 `<symbol id="i-新名字" viewBox="0 0 16 16">`，然后 `iconEl('新名字')` 即可。**不要**为新图标新建 `<svg>` 节点。

### 4.3 何时用 CSS mask data-URI

| 场景 | 做法 |
|---|---|
| **动态生成的图标**（聊天流、消息操作行、chip 内图标、浮层项图标） | `iconEl()` → `<span class="ico-mask">` + `mask-image` |
| **纯装饰、位置固定、颜色随文字** | 同上（`iconEl` 一样能用） |
| **需要多个色块 / 渐变 / 多路径异色** | sprite `<svg>`（`<use href="#i-x">`），**仅限静态外壳** |
| **品牌 mark（球 26px / 头部 16px 渐变气泡 + π）** | sprite `<svg>` + `<linearGradient>`（渐变无法用单色 mask 表达） |

> **mask 的固有限制**：mask 只取 alpha 通道，**一个图标只能一种颜色**。需要多色 → 用 sprite `<svg>`，但 sprite 只能放在**静态外壳**（`<body>` 顶层），**不能**进聊天流。

### 4.4 静态外壳用 sprite `<svg>` 的例外边界

**允许**（且仅允许）：

```html
<!-- 静态外壳：sprite 本体 -->
<svg id="iconSprite" aria-hidden="true" focusable="false"
     style="position:absolute;left:0;top:0;width:0;height:0;overflow:hidden">
  <defs>
    <linearGradient id="ballBubbleGrad" x1="0" y1="0" x2="1" y2="1">…</linearGradient>
    <symbol id="i-copy" viewBox="0 0 16 16">…</symbol>
  </defs>
</svg>

<!-- 静态外壳里的引用：scrollpill 按钮（大窗静态 chrome） -->
<button class="scrollpill" id="scrollPill" type="button" hidden aria-label="回到最新">
  <svg class="scrollpill__i" aria-hidden="true"><use href="#i-chevron-down"/></svg>
</button>
```

**边界**：

| 规则 | 理由 |
|---|---|
| sprite 本体**不能加 `hidden`** | `display:none` 子树上部分浏览器解析不到 `<symbol>` / `<linearGradient>` —— 用 `width:0;height:0;overflow:hidden`（现状 `index.html:1306-1309`） |
| `<use href="#i-x">` 的引用**只能出现在静态 HTML** | 一旦由脚本插入到聊天流，就变成 `#miniBody` 里的 `<svg>` → C5 判 P0 |
| 渐变 `id` **全文档唯一** | 球与 mini 头部同时在 DOM（形态切换只切 `hidden` 不重建 DOM），id 重复会串色 |
| 品牌渐变**只定义一次** | `ballBubbleGrad` / `ballFaceGrad` / `ballEdgeGrad` / `ballPiGrad` 供 26px 球与 16px 头部共用 |

> **判定口诀**：**外壳的 `<svg>` 是"图片"，聊天流的 `<svg>` 是"载荷"。** 门禁分不清，所以聊天流一律用 mask。

| 动效降级 | `prefers-reduced-motion: reduce` 下动效降级后状态**仍可读** |

> **对比度实测方法**：`qa-theme.mjs` 的 `[F]` 组在 headless Chrome 里取 `getComputedStyle(document.documentElement)` 的令牌值，用 WCAG 相对亮度公式实算。**新增文字令牌时要往该组补断言**（否则新颜色没人算）。

### 5.5 纪律：「新增门禁必须做变异验证」

> **这条是本章最重要的纪律。没有做过变异验证的断言，不算守护。**

**变异验证（mutation testing）= 把实现改坏，看门禁会不会红。**

| 步骤 | 动作 | 期望 |
|---|---|---|
| 1 | 复制一份渲染层到临时文件 | 不碰真文件 |
| 2 | 故意破坏一处（例：把 `.mini` 的 `box-shadow` 改成外扩 `0 8px 20px`） | — |
| 3 | `node scripts/qa-future-ui.mjs <临时文件>` | **必须 FAIL**，且失败信息指向 C1 |
| 4 | 换一处破坏（例：把 `--fx-lit-top` 从四个块里删掉三个） | **必须 FAIL**，指向 A1/A2 |
| 5 | 恢复真文件，确认 `node scripts/qa-future-ui.mjs` 仍全绿 | 必须 PASS |

**判定**：

- 门禁**没红** → 这条断言是**假守护**（要么它没覆盖你改的地方，要么它恒真）。
- 门禁**红了但信息指不到根因** → 断言可读性不合格，要改门禁（`scripts/` 可改，`src/` 不改）。
- **没有验证过的断言 = 不存在。** 新增门禁断言时，**必须**至少做一次变异验证，并在 PR 描述里写清「改了哪一处 → 哪条断言红了」。

> 现成的变异入口：`qa-future-ui.mjs` 的第二个参数就是为变异验证设计的（脚本头部注释原文：「可选路径参数供变异验证用：对临时副本跑，绝不碰真文件」）。

## 7. 常见坑清单

> 每条格式：**症状 → 根因 → 正确写法**。

### 坑 1 · 令牌漏写三块，强制主题下样式静默失效

- **症状**：跟随系统时一切正常；手动切到"浅色"或"暗色"后，某个新装饰（顶边高光、网格、卡片浮起）**整块消失**；DevTools 里看到 `var(--fx-xxx)` 解析为空。没有报错、没有警告。
- **根因**：新增令牌只写进了 `:root` 与一个覆盖块。`html[data-theme="dark"]` 的优先级最高，未定义的令牌在该作用域下 `var()` 解析失败 → 整条声明失效 → 元素退回浏览器默认样式。
- **正确写法**：**四处全写**（§2.2 第 3 步分支 A），然后跑 `node scripts/qa-future-ui.mjs` 看 `[A] A1/A2` 是否 PASS。

### 坑 2 · 焦点环外扩，被窗口边界裁掉一半

- **症状**：贴边小按钮（图标按钮、消息操作行按钮）获得焦点时，焦点环缺一边，看着像"渲染坏了"。
- **根因**：`outline-offset` 取 `2px`，环向元素外扩 2px + 自身 2px 宽 = 距元素边缘 4px；元素距窗口边缘不足 4px 时被窗口矩形裁掉。
- **正确写法**：`outline-offset` 取 **1px**（组件规格裁剪坑 11）。> **现状是 `2px`**（`src/renderer/index.html:216` 与 `:1137`），属**已知差异**，记录在案不改（见 `03-交互与状态规范.md` §9.1）。新增组件的焦点环请直接取 `1px`。

### 坑 3 · hover 用缩放，48px 球与窗口边缘出现透明缝

- **症状**：按下悬浮球时，球和窗口边缘之间出现一圈 0.7px 的发虚缝；hover 时球被"切掉一刀"。
- **根因**：`transform: scale(.96)` / `scale(1.06)`。48px 窗口里缩放后元素不再与窗口矩形重合，缩出来/缩进去的部分露出透明区。
- **正确写法**：**禁止 `scale()`**（门禁 C2 硬判）。press 反馈用 `inset box-shadow` 加深（`.ball--sphere:active`，`index.html:335-340`），hover 用 `border-color`（`.ball:hover{ border-color:var(--ball-hover-border); }`）。位移 `translateY(1px)` 可以。

### 坑 4 · π 读作"洞"而不是"凸"

- **症状**：球心的 π 看起来像被挖掉一个洞，或者下端和气泡底色融在一起，浮雕感消失。
- **根因**：π 的最暗端（`--ball-pi-lo`）亮度**低于**气泡底色（`--accent`），或 `--ball-ink` 被改回近黑。暗色主题下尤其明显。
- **正确写法**：π 三端亮度必须**都高于**气泡底色（门禁 E2 实算 sRGB 相对亮度）；`--ball-ink` 暗色不低于 `#0b1220`（门禁 E3）。改 π 任何一端都要三端 + 气泡两端一起复核。

### 坑 5 · 图标触发 XSS 门禁

- **症状**：`node scripts/qa-renderer-edge.mjs` 报 P0 / `C5-XSS`；`qa-future-ui` 的 `[G]` 组 G1 报「`#miniBody` 容器内 HTML 零 `<svg>` 元素」FAIL。**但代码里并没有注入脚本**。
- **根因**：聊天流里用了 `<svg>` 节点画图标。C5 判定口径是"真实 DOM 里存在 `svg` 元素"，**分不清图标与 `<svg onload>` 载荷**。
- **正确写法**：动态图标一律 `iconEl(name, size, cls)` → `<span class="ico-mask">` + `mask-image`；需要多色/渐变时才用 sprite `<svg>`，且**只能放静态外壳**。脚本里不要 `innerHTML` 拼 `<svg>`。

### 坑 6 · 硬编码颜色触发主题门禁

- **症状**：`node scripts/qa-theme.mjs` 的 `[B]` 组 FAIL：「组件样式里没有硬编码 hex / rgba」；或 `[B2]` 组 FAIL：「脚本里没有硬编码颜色字面量」。
- **根因**：新组件里写了 `#4c9aff` / `rgba(76,154,255,.14)`，或 JS 里 `el.style.color = '#ff9d96'`。这类值**不随主题变** —— 浅色主题下就是浅粉压白底。
- **正确写法**：颜色全部走 `var(--令牌)`；需要透明度用 `color-mix(in srgb, var(--令牌) N%, transparent)`；JS 里写 `el.style.color = 'var(--danger-ink)'`。

### 坑 7 · 引用了不存在的令牌（`var()` 静默失败）

- **症状**：某段样式的属性"完全不起作用" —— 不是被覆盖，是**根本没生效**（如输入框文字颜色不跟随主题、背景不跟随）。DevTools 里该条声明呈**划线**状态。
- **根因**：`var(--令牌名)` 里的令牌名拼错或根本没定义。`var()` 解析失败时，**整条声明作废**（不是回退到 `inherit`，也不是回退到初始值）—— 只影响这一条声明，很容易被忽略。
- **正确写法**：`var()` 的令牌必须在四块中**确实存在**。`qa-future-ui` 的 A5 组会检查**新令牌**内部引用的令牌可解析，但**不会**检查组件区的引用 —— 组件区的引用要人工核对。

> **现存的真实例子**（`src/renderer/index.html:552-556`，`.approval__instr textarea`）：`color:var(--text-1)`、`background:var(--surface-sunken)`、`border:1px dashed var(--line-strong)`、`::placeholder{ color:var(--text-3) }` —— 这四个令牌在四个令牌块里**都不存在**。结果是这四条声明**全部静默失效**。本文件**只记录不改代码**（`src/` 不在本任务范围），但**新增代码不得复制这个写法**。

### 坑 8 · 浮层贴边被裁出一圈暗边

- **症状**：导出 popover、能力菜单打开时，靠近窗口边缘的一侧有一圈暗边/淡边。
- **根因**：浮层用了外扩阴影（`--shadow-1/2`），而浮层锚在窗口边缘附近，阴影溢出部分被窗口矩形裁掉。
- **正确写法**：贴边浮层**只用 inset**（现状 `.popmenu` / `.capmenu` / `.cmdpanel`，`index.html:1162-1192`）。外扩阴影 `--shadow-1/2` **只**给"距窗口边缘 ≥40px 的居中面板"（命令面板、设置面板）。

### 坑 9 · 轴线用 `border-left`，正文被挤动 1px

- **症状**：助手消息正文与轴线之间多出 1px 空隙；轴线随容器宽度变化而抖动。
- **根因**：`border-left` 参与盒模型宽度计算，会把内容区挤窄 1px。
- **正确写法**：用**绝对定位伪元素**画 1px 渐变条（`.msg--pi::after`，`index.html:701-704`）。

### 坑 10 · 网格被底色压住 / 渗进代码块

- **症状**：小窗里网格看不见（死板），或代码块里出现网格线（干扰阅读）。
- **根因**：给 `.msg` / `.pibody` 加了实底色；或把 `--fx-grid` 用到了代码块 / diff 内部。
- **正确写法**：网格**只铺容器底**，正文行保持透明（`.scroll > .msg{ background:transparent; }`）；代码块用 `--code-bg` 且不铺网格。门禁 F2 / F4 分别守这两条。

### 坑 11 · 状态色爆表（整块彩色面积）

- **症状**：产出卡 / 审批卡整个变成彩色块，与"冷调仪器面板"的克制感冲突。
- **根因**：用状态色做了**大面积背景**，而不是"2px 语义边 / chip 底 / 状态文字"三种载体之一。
- **正确写法**：状态色只允许出现在 **2px 语义边 / chip 底 / 状态文字** 上（`03-交互与状态规范.md` §1.3）。产出卡成功用 `--success` 左边框、审批卡用 `--warn` 左边框、其余面积保持中性。

### 坑 12 · 新令牌只改了规格文档、没改代码（或反之）

- **症状**：`qa-future-ui.mjs` 报 `A1`「某块缺失全部主题相关新令牌」；或报 `fatal`「规格令牌解析失败」。
- **根因**：门禁的令牌名单是**运行时从 `ui-optimization/future-ui/02-令牌规格.md` 的表格里解析**的（`scripts/qa-future-ui.mjs:65-74`），代码与规格必须同步。
- **正确写法**：新增令牌 = 改**代码四块** + 改**规格文档表格**（表格首列写 `` `--新令牌名` ``），两件事一起做。
