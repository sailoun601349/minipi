# minipi 前端 UI 规范 · 总纲

> **这是开发团队做前端功能时的唯一权威依据。**
> 本规范是「设计意图 → 可机械检查的判据 → 可执行流程」的翻译层，不是灵感集。
> 任何与本规范冲突的实现，以本规范为准；本规范与代码冲突时，**先停下来说清楚**，不要默默绕过。

---

## 0. 一句话

**minipi 是一台常驻在桌面边缘、按需呼出的仪器化助手，不是聊天 App。**
它的界面语言是「被冷光照亮的精密仪表」：面板分层靠明度、边界靠 1px 发丝线、状态靠轴点与读数。
科技感来自**秩序与读数**，不来自霓虹、噪点与动效。

---

## 1. 这份规范解决什么问题

开发团队接新功能时，最容易出的问题不是「做得不好看」，而是：

| 典型症状 | 根因 | 本规范怎么防 |
|---|---|---|
| 每个功能长成另一个样子 | 没有共享的视觉语言，只有"上次那样挺好" | §1 视觉定位 + §2 令牌体系是**唯一真源** |
| 加一个功能要改 6 个文件、样式互相打架 | 没有明确的实现落点与边界 | §5 新功能接入流程（Step 0 先定边界） |
| 写完不知道对不对，全凭肉眼 | 判据不可验证 | 每条原则都有**可机械检查的判据**，且已有门禁守着 |
| 主题切过去有一处颜色不对 | 令牌四块漏写 | §2.3 新增令牌四步法（**四处全写**） |
| 窗口边缘出现一圈淡边 | 在透明窗里用了外扩阴影 | §3.1 透明窗裁剪铁律（**只允许 inset**） |
| 聊天气泡里图标被安全检查拦下 | 聊天流里注入了 `<svg>` | §4 图标规范 |

## 3. 视觉定位（速览，详见 §1 分册）

### 3.1 视觉人格三词 + 可判定标准

| 人格词 | 含义 | **可判定标准**（能一眼判断，不靠感觉） |
|---|---|---|
| **精密** | 边界清晰、层次分明、读数准确 | 明度分层不少于 4 级；边界只用 1px 发丝线不用粗边框；数字一律等宽 tabular |
| **克制** | 不炫技、不抢注意力、状态色克制 | 实色主色块 ≤64px；`var(--accent)` 引用处数 ≤60（现状 52）；彩色面积 <5%（目标 <2%） |
| **可信** | 像仪器而不像玩具；反馈明确不含糊 | 每个可点元素有 hover/focus/active 三态；异步操作有进行中态；失败必给可执行的下一步 |

### 3.2 我们明确不做的（区隔通用 AI 聊天窗口）

| 不做 | 原因 |
|---|---|
| 消息气泡 | 气泡 = 亲和，但我们要「仪器读数」。助手消息去气泡，改用轴点 + 渐隐轴线 |
| 霓虹外发光 / 噪点 / 玻璃拟态模糊 | 外发光落在透明窗角区会渲染成淡边（用户投诉两次）；噪点与模糊在 48px 球上完全失效 |
| `transform: scale()` 做 hover/press | 缩放会让 48px 球与窗口边缘出现 0.7px 透明缝 |
| 多彩渐变、大圆角 + 厚阴影 | 破坏明度阶梯，让面板读起来像消费级 App |
| 密集动效 | 悬浮助手是常驻窗口，动效成本持续付 |

## 4. 令牌是唯一真源（速览，详见 §2 分册）

### 4.1 四块结构（漏一处 ⇒ 强制主题下样式静默失效）

```
优先级 低 ────────────────────────────────────────────► 高

:root                       ① 暗色兜底（永远存在）
  └ @media (prefers-color-scheme: light) :root   ② 跟随系统时的浅色
      └ html[data-theme="light"]                ③ 手动强制浅色
          └ html[data-theme="dark"]             ④ 手动强制暗色
```

- **主题相关**令牌（值是具体颜色/阴影）→ **四处全写**。
- **主题无关**复合值（值内部引用别的颜色令牌，如 `--fx-grid`）→ **只在 `:root` 定义一次**，自动跟随主题。
- 组件区（令牌块之外）**零 hex、零 `rgba()`** —— 有门禁守。

### 4.2 令牌生命周期：没有消费者的令牌就是负债

```
定义 → 有消费者 → （改值不改名）
                  ↓
             没有消费者 → 删除（四处同步删）
```

判定命令见 §2 分册 §2.4。**已清理过的实例**：`.dot` / `.meter` / `.ticks` / `.scan` 及 13 个配套令牌，
2026-10-22 已从产品与设计文档中彻底移除。

## 5. 开发团队执行总则（提交前必须逐条过）

### 5.1 硬约束（违反即阻塞合并）

| # | 约束 | 判定方式 |
|---|---|---|
| 1 | 组件区不写死颜色，一律用令牌 | `qa-theme` 门禁 |
| 2 | 窗口级元素（`.ball` / `.mini` / `.full`）只允许 `inset` 阴影 | `qa-future-ui` C 组 |
| 3 | 全局零 `transform: scale()` | `qa-future-ui` C 组 |
| 4 | 聊天流 `#miniBody` 内零 `<svg>` 元素 | `qa-renderer-edge` C5 |
| 5 | 新增主题相关令牌四处全写 | `qa-future-ui` A1 / A2 |
| 6 | 零外链：无 `@import`、无 `url(http…)`、无外链字体与脚本 | `qa-future-ui` H 组 |
| 7 | 不引入框架 / 预处理器 / 构建步骤 | 代码评审 |
| 8 | 不改 Pi 的 `auth.json` / `models.json` | 代码评审 |

### 5.2 流程纪律

1. **新门禁必须做变异验证**：把实现改坏 ⇒ 门禁必须红。没红过的断言不算守护。
2. **证据必须对指纹**：长任务跑前跑后取 sha256；文件在跑动中被改过 ⇒ 那批证据作废。
3. **截图必须真实产出**：用真实渲染层实拍，禁止伪造或用示意图冒充实拍。
4. **"没测到" ≠ "测过了但失败"**：测不到一律记 `null`（报告显示 n/a），不要记 false。
5. **测试失败要逐测试隔离**：一个挂不能连坐后面的。

### 5.3 提交前自检清单

```bash
# 1) 主题与令牌
node scripts/qa-theme.mjs

# 2) 未来感硬约束（58 条断言 / 8 组）
node scripts/qa-future-ui.mjs

# 3) 渲染边界（聊天流零 svg 等）
node scripts/qa-renderer-edge.mjs

# 4) 全量回归（当前 30 个脚本）
node scripts/verify-all.mjs
```

四步全绿才算完成。**任一步红 → 不要解释"环境抖动"，先复跑两遍；稳定红就是代码/测试有问题。**

## 7. 怎么用这份规范

| 场景 | 动作 |
|---|---|
| 接一个新功能 | 从 §2 分册 §5「新功能接入流程」的 **Step 0 前置检查**开始 |
| 改一处样式 | 先查 §2 分册 §2.2「新增 vs 复用判据」——大概率不需要新令牌 |
| 加一个交互状态 | 查 §3 分册 §2 状态机清单 + §3 反馈梯度选级 |
| 评审别人的 PR | 用 §5.1 硬约束表逐条过；视觉主观部分用 §1 分册 §7 自查清单 |
| 想改视觉方向 | 先看 `ui-optimization/future-ui/01-视觉方向.md` 的四方向评分与 A 的五条理由，**不要凭单点感受推翻** |

## 8. 维护

- 本规范随产品演进更新；每次视觉方向变更或令牌体系变更，**必须同步更新对应分册 + 门禁**。
- 分册与产品代码的漂移由门禁 `qa-future-ui`（令牌名单运行时解析）自动暴露 —— 它红了就说明文档与代码不同步了。
- 规范本身也需要版本记录：改动请在对应分册末尾的「变更记录」里追加一行（日期 / 改了什么 / 为什么）。
